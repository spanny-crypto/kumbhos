# Data Sources & Provenance

This mirrors the in-app `/data-sources` page (`/api/data-sources`, generated by
`src/lib/data/seed/generate.ts:generateDataSources()`). Every record the app produces carries a `dataSource` field
so provenance is traceable in the API response itself, not just documented separately.

| Dataset | Publisher | Type | Status |

## Why the government datasets are stubbed, not faked

The brief for this build is explicit: never claim a live government feed, never fabricate an integration. Importing
and normalizing `data.gov.in` resources (encoding quirks, missing coordinates, license attribution, refresh
scheduling) is real engineering work that wasn't attempted for tonight's build. Building a fake-looking "government
data" adapter that actually just re-labels synthetic numbers would violate that principle, so instead:

- The dataset entries exist and link to their real, verifiable source URLs.
- Their `status` is `STUBBED`, and the UI badge for `GOVERNMENT_OPEN_DATA` type is visually distinct from
  `SIMULATED`.
- `docs/ARCHITECTURE.md` documents the intended adapter shape (`GovernmentSanitationAdapter`,
  `GovernmentWasteAdapter`) as future work.

## Adding a real adapter later

1. Add a module under `src/lib/data/adapters/` that fetches + validates + normalizes the source into our `Toilet[]`
   / `InfrastructureAsset[]` shape (see `src/lib/data/types.ts`).
2. Reject and log invalid records rather than guessing missing fields (especially coordinates — never invent a
   lat/lng that isn't in the source).
3. Update the corresponding `data_sources` row's `status` to `ACTIVE` and `dataType` to `GOVERNMENT_OPEN_DATA`, with
   real `dateObtained`/`lastUpdated` values.
4. Wire it into `SupabaseDataProvider` (or a new provider) behind the same `DataProvider` interface — nothing else in
   the app needs to change.
